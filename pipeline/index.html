Lifecycle

Truth tree → code, and back

Six stages, each with an exact command and a green/red gate. The loop is closed twice: once forward (tree → graph → code), once backward (code → anchors → tree). The numbers below are the bank worked example, re-captured 2026-11-11.

01

The six stages

01 · AUTHOREdit the tree

YAML atoms only. Agents draft, humans approve — approvedBy recorded per atom.

02 · GATEValidate + roundtrip

validate 0 hard; roundtrip byte-identical. 157 atoms ✓

03 · GRAPHCompile & push

Canonical projection → SQLite graph: 389 nodes / 413 edges.

04 · GENERATECQRS codebase

generate-project: 235 files, 0 compile errors.

05 · HANDWRITEFill the zone

Ports are generated; behavior goes in the physically separate handwritten module — 35 files, complete implementations.

06 · VERIFYProve lineage

verify-project: 792 anchors; tests 23/23.

And then it loops: change the tree, status-project shows exactly which generated files went stale, generate-project --update refreshes only those, re-running on an unchanged tree writes 0 files (idempotence is a gate, not a hope).

02

Anchors: the part nobody else ships

Generation is common. Proof of origin is not. Every generated file carries anchor metadata binding it to the knowledge node that produced it — and the binding is verified by re-reading bytes, not by trusting a manifest.

two directions, one command each
$ truthsrc query-project --knowledge SetCount
  knowledge  rule:SetCount (aggregate example/Counter)
  generated  app/domain/example/Counter.scala  L31–L54   ← span, not guess

$ truthsrc query-project --file app/domain/example/Counter.scala --symbol setCount
  source     slice example/set-count  →  guards  →  rule:SetCount

$ truthsrc verify-project --project truthsrc.project.json --out app/
✓ passed — every anchor re-verified against file bytes (792 on the bank project)
Why it matters

“Where did this line come from?”

A compliance question, a debugging question, and an onboarding question — answered by query, not by archaeology.

Why it’s honest

Byte-precision, not vibes

Anchors record spans; verification re-reads the file. If a human edits generated code, verification reports drift instead of silently re-trusting.

Why agents need it

No-grep context packs

The same anchor graph packages exact upstream types, caller contracts and acceptance scenarios for a handwriting agent — closing the loop for AI collaborators.

03

The handwritten zone

The generation philosophy: generate the ports, leave the behavior to people (and their agents) — but only in a physically separate module that regeneration can never touch.

Generated side

Everything structural

Aggregates, commands, events, guards (compiled from @rule invariants), proto schemas, ports, test scaffolding — 235 files in the bank project, all regenerable, all anchored.

Handwritten side

Everything behavioral

Effect execution against the mock TA, JDBC wiring, recovery loops, the read-side catch-up, HTTP pages — 35 files, complete implementations verified, mounted into the build via unmanagedSourceDirectories. No BEGIN MANUAL markers anywhere — the boundary is the filesystem.

DRIFT

When the tree changes, generated files are refreshed; the handwritten zone is never overwritten. The tests stay fixed as expectations — the generated code must satisfy the handwritten tests, not the other way around. 23/23 pass today verified.

04

Where saga & Monarch come in

Two engines, two jobs — declared in truth, never confused:

saga-core · TCC transactions

Cross-aggregate consistency

A saga atom declares participants (aggregates), phases (Try / Confirm / Cancel) and compensation. It compiles to saga IR for saga-core — an Akka Typed, event-sourced TCC coordinator. The bank tree declares 2 sagas: cash payment (investor outgoing → collection incoming → order commit) and the independent refund.

monarch-core · stage queues

Flow orchestration

A pipeline atom is an ordered business-step queue; steps execute slices (R16). It compiles to a plan for monarch-core — a recoverable stage-queue engine with cursor-based resume, journaled by monarch-persistence. The bank tree declares 4 pipelines (cash payment, TA submission, SIP dispatch, independent refund).

The rule that keeps them straight: Sagas own transaction boundaries; pipelines own flow order. They are not interchangeable, and the truth tree refuses to blur them.
