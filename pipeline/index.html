The engineering loop

What is generated,
and what remains yours?

Keep domain knowledge, technical bindings and handwritten integration in their proper places. Compile the declarations, inspect the generated changes, test the behavior, then trace the implementation back to its source.

01

A lifecycle with explicit responsibilities

01 · AUTHORAgree on the behavior

Edit the truth tree for knowledge. Review the business expectation; record human approval through the project’s review process.

02 · GATEValidate the source

Validation checks structure and supported semantics; roundtrip checks preservation. Neither substitutes for a business test.

03 · COMPILEDerive products and graph

Compile declarations into products and build the queryable graph. Do not hand-edit these derived knowledge representations.

04 · GENERATEPreview, then write

Use the project’s technical bindings. Inspect the generation plan before writing supported behavior and structural code.

05 · INTEGRATEImplement host responsibilities

Keep external effects and remaining computations in the separate handwritten zone. Test them against agreed outcomes.

06 · VERIFYCheck code and origin

Compile and run the appropriate tests. Verify source anchors and output freshness; investigate drift before updating.

status-project distinguishes changed inputs from output-byte drift; generate-project --update --plan lists prospective actions, not a textual diff. Derive reverse-query line numbers from a verified UTF-8 span and matching source bytes, never a guessed filename or line.

02

Ask where an implementation came from

A source anchor connects a knowledge declaration to a generated location. The useful answer includes identity, precision and freshness—not just a plausible filename.

Origin

A relation, not a correctness proof

An anchor supports “this location came from this declaration.” It does not establish that the declaration was approved or that every line of the program is correct.

Precision

Span and file are different answers

A span identifies a byte range; file identifies only a file. Treat ambiguous or unavailable as a limit, not permission to guess a line.

Freshness

Check the matching bytes

Use source fingerprints and verification before translating a UTF-8 byte span into a line number. A graph snapshot without matching code locations cannot supply a precise code jump.

The Counter guide walks both query directions using an actual verified location. It also explains stale inputs, output drift and updates. A canonical graph, a project knowledge graph and a workshop export are different representations; do not splice their identities together by name.

03

Edit the layer that owns the change

Generate supported, declared behavior; handwrite the remaining computations and host integration. The tree is the only knowledge editing surface—not the only editable file in the project.

Truth + generated side

Domain declarations

Aggregates, commands and events, together with supported guard, binding and fold declarations, drive generation. Structure includes schemas, ports and test scaffolding. An invariant name alone does not implement a missing rule.

Explicit input

Technical bindings

Bindings connect the declared model to the chosen implementation profile and host contracts. Review them separately from business policy; generated products are not a second place to edit the same knowledge.

Handwritten zone

Host integration

Mock TA effect execution, JDBC wiring, recovery loops, read-side catch-up and HTTP pages remain explicit implementations. The bank’s 35 handwritten files were recorded as complete implementations F-08 · 2026-11-11.

The bank build includes its separate handwritten module through unmanagedSourceDirectories. The filesystem boundary keeps it outside normal regeneration; it is not a promise that arbitrary output paths or unrelated tools cannot overwrite files.

TEST SCOPE

When the tree changes, generated files are refreshed; the handwritten zone is not overwritten. The 23/23 result from 2026-11-11 is generated unit tests F-07: handwritten production sources compile with that build, but this is not evidence of independent handwritten test expectations. In the newer technical candidate, actor 64 and readside 47 passed with fixed business expectations; those scopes share 23 generated tests and must not be summed as distinct cases F-25.

04

Where saga & Monarch come in

Two engines, two jobs — declared in truth, never confused:

saga-core · TCC transactions

Cross-aggregate consistency

A saga atom declares participants (aggregates), phases (Try / Confirm / Cancel) and compensation. It compiles to saga IR for saga-core — an Akka Typed, event-sourced TCC coordinator. The bank tree declares 2 sagas: cash payment (investor outgoing → collection incoming → order commit) and the independent refund.

monarch-core · stage queues

Flow orchestration

A pipeline atom is an ordered business-step queue; steps execute slices (R16). It compiles to a plan for monarch-core — a recoverable stage-queue engine with cursor-based resume, journaled by monarch-persistence. The bank tree declares 4 pipelines (cash payment, TA submission, SIP dispatch, independent refund).

The rule that keeps them straight: Sagas own transaction boundaries; pipelines own flow order. They are not interchangeable, and the truth tree refuses to blur them.
