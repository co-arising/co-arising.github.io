Landscape

Peers, complements & the ontology next door

This space has good neighbors. The honest positioning: some tools we complement, some we extend, one we respectfully disagree with about what “model” means. None of this is a star-count contest — it is about which job each tool does.

01

The peers, job by job

ProjectWhat it isLicense / modelWhere we overlapWhere we differ / complement
EventCatalogdocs-as-code for event-driven systems Domains, services, events and schemas rendered as a browsable catalog. v4 adds an agent/MCP layer. MIT · open core Event-driven knowledge as a first-class graph; MCP for agent access — same instincts. The cleanest one-liner in the space: EventCatalog generates docs from your architecture; we generate the architecture itself, from knowledge — and anchor it back. Their Code-to-Docs agent is code → docs; our loop is knowledge → code → provenance. Natural complement, not rival.
ContextMapperDDD DSL (CML) A textual DSL for bounded contexts, context maps, aggregates; generates PlantUML / MDSL. Apache-2.0 · academic origin File-based DDD modeling with generators — the closest ancestor in spirit. CML captures strategic + tactical shape; it stops at diagrams and contracts. Our tree compiles to a knowledge graph with query verbs, generates a compiling CQRS codebase, and proves lineage with anchors. CML output could ride downstream of a truth tree as one projection among several.
proophPHP CQRS/ES components · Event Engine Event-sourcing toolkit in PHP; Event Engine pioneered “type a model, generate ES code”. MIT · community/mixed The “model → generated ES code” ambition — they proved the demand is real. Their audience is PHP runtime plumbing; ours is the knowledge layer above any runtime — with validation gates, graph queries, agent access and anchored round-tripping. Different layer, same belief.
QlerifyAI-assisted collaborative modeling SaaS Event-storming-style canvas, AI proposes commands/events/models, exports backlogs + OpenAPI. Proprietary SaaS AI-assisted discovery of commands/events/read models — overlapping front-end of the funnel. Field-level analysis of a real Qlerify export: skeleton full, behavior empty — aggregates/events/roles/queries export cleanly (5/15 of our types fully), but invariants, guards, error codes, sagas and pipelines have no representation (their strategy/decision/GWT cards are narrative text, not formal). Qlerify discovers consensus; a truth tree turns it into industrial artifacts. Integration — including reverse export back to the canvas — is designed for, on the DEF-02 ledger.
EventStorming / Domain Storytellingdiscovery methods Workshop formats: orange events, blue commands, actors, policies — or actor/workpiece/activity narratives. Methods, not tools Our inbox note types ARE the sticky-note vocabulary — EventStorming is the canonical intake. A method is not a source of truth: photos of walls rot. The inbox is where workshop output lands as machine-checkable drafts awaiting human promotion — the discovery layer we deliberately don’t compete with, we consume.
Palantir Ontologyenterprise semantic layer Object/link/action types over enterprise data; actions write back; SDKs generated from types; MCP exposure. Proprietary Generated SDKs from a semantic model; “decisions, not just data”; agent access — deeply aligned instincts. Closed world vs open files: their ontology is the product you rent; our tree is YAML you own, compiling to code you can leave with. Taxonomy-first vs relation-first — the philosophical fork this site is named after. We borrow their governance thinking (usage tracking, staged changes); we publish the stack.

Coverage numbers for Qlerify come from a field-level analysis of a real exported workflow.json against our 15-type registry — 5 full / 6 partial / 4 absent. Method and matrix available in the project’s research notes.

WHY PROJECTIONS

A projection is regenerable, so it can adopt the best standard for each consumer without the tree owning N dialects. The standard never becomes the master; the tree never forks into N files that drift apart. (Projection generators beyond MCP + SQLite are sequenced after the runtime gates on the ledger.)
