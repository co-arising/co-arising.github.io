How do we keep a business decision connected to the code that implements it? Write the concepts, rules and behavior in a readable truth source. Generate the supported implementation, keep integration explicit, and trace changes back to their declarations.

Explore the bank example Try Counter
A real declaration · not a running console

What makes a count change valid?

  1. Command. Counter.SetCount receives id and count.
  2. Guards. Require param.id.nonEmpty and param.count >= 0. Failure rejects with EMPTY_ID or NEGATIVE_COUNT.
  3. Event + bindings. On acceptance, CountSet takes its id and count from the command.
  4. State fold. The event sets state id from event.id and count from event.count.

A reading of the pinned Counter source, not a simulated result. See the declaration and fold explained.

01

Keep the decision and its implementation connected

The smallest useful loop is truth tree → compiled products → generated code → source anchors. Each part answers a different question; no single green gate proves the business decision right.

Describe

What must remain true?

Use a file-based truth tree to name aggregates, commands, events and invariants. People can review the business rules before discussing implementation details.

Explore

What depends on this?

Query declared relationships in a local SQLite knowledge graph. Explore the bank snapshot; the graph can only show dependencies that have been modeled.

Generate

Which behavior is declared?

Supported guards, event bindings and state folds become code alongside CQRS/ES structure. Generation does not invent missing business policy.

Integrate

What remains handwritten?

Technical bindings and a separate handwritten zone connect the generated project to external effects and host services. Their responsibilities and tests stay explicit.

Trace

Where did this implementation come from?

Source anchors connect knowledge to generated code at the precision supplied. Verification checks freshness and bytes; it is not proof that every line is correct.

Review

Who approves a change?

People and agents can query, propose and test. Humans approve the intended behavior. Technical passes, independent experience and delivery remain separate on the status ledger.

02

Make one change in your own project

Use Node ≥ 22.13 in a new exercise directory. Acquiring the source checkout needs a network; the Counter generation loop needs no JVM or database service. The full walkthrough — including the bank example and the MCP integration — is on the hands-on guide.

Expand the first-generation commands 
export TRUTHSRC_WORKSPACE="$PWD"
git clone https://github.com/co-arising/metarch-truthsrc.git
export TRUTHSRC_CLI="$TRUTHSRC_WORKSPACE/metarch-truthsrc/bin/truthsrc.js"
node "$TRUTHSRC_CLI" init counter-lab --format human
cd counter-lab
node "$TRUTHSRC_CLI" generate-project --project truthsrc.project.json --out generated --plan --format human
node "$TRUTHSRC_CLI" generate-project --project truthsrc.project.json --out generated --format human
node "$TRUTHSRC_CLI" query-project --project truthsrc.project.json --out generated --knowledge SetCount --format human
node "$TRUTHSRC_CLI" verify-project --project truthsrc.project.json --out generated --format human
