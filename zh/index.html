co-arising · 共享知识，明确变更责任

让业务知识可共识、
实现可验证、
变更可追溯。

业务决策如何始终与实现它的代码相连？把概念、规则与行为写进可读的真源，生成工具支持的实现，明确保留集成职责，再从代码追溯到相应声明。

真实声明 · 不是运行中的控制台

一次计数变更，凭什么成立？

  1. 命令。Counter.SetCount 接收 id 与 count。
  2. 守卫。要求 param.id.nonEmpty 且 param.count >= 0；不满足时以 EMPTY_ID 或 NEGATIVE_COUNT 拒绝。
  3. 事件与绑定。接受命令后，CountSet 的 id、count 取自命令参数。
  4. 状态折叠。事件把状态的 id 设为 event.id，把 count 设为 event.count。

这是对固定版本 Counter 源码的讲解，不是模拟执行结果。继续读声明与状态折叠。

01

让业务决策与实现保持联系

最小实用闭环是真源树 → 编译产物 → 生成代码 → 来源锚点。每一环回答不同的问题；任何一道绿灯，都不能单独证明业务决策正确。

描述

哪些条件必须始终成立？

在文件真源树中明确聚合、命令、事件与不变量。讨论实现细节之前，先让人能一起审阅业务规则。

探索

什么依赖这项知识？

在本地 SQLite 知识图谱中查询已声明的关系。可以先探索银行快照；图谱只能显示已建模的依赖。

生成

哪些行为已经声明清楚？

受支持的守卫、事件绑定与状态折叠，连同 CQRS/ES 结构一起生成。缺失的业务政策不会由生成器代为决定。

集成

哪些仍需要手写？

技术绑定与独立的手写实现区，把生成项目接到外部效果和宿主服务。各自的职责与测试不被生成过程掩盖。

追溯

这段实现来自哪项知识？

来源锚点按实际提供的精度连接知识与生成代码。验证检查新鲜度和字节，不等于证明每行代码都正确。

审阅

谁来批准变更？

人与智能体都可以查询、提议和测试；预期业务行为由人批准。技术通过、独立体验与交付在状态台账中分别记录。

02

在自己的项目中改一次

在新的练习目录中使用 Node ≥ 22.13。取得工具源码需要网络；Counter 生成闭环不需要 JVM 或数据库服务。包含银行示例与 MCP 集成的完整教程在实战指南。

展开首次生成命令 
export TRUTHSRC_WORKSPACE="$PWD"
git clone https://github.com/co-arising/metarch-truthsrc.git
export TRUTHSRC_CLI="$TRUTHSRC_WORKSPACE/metarch-truthsrc/bin/truthsrc.js"
node "$TRUTHSRC_CLI" init counter-lab --format human
cd counter-lab
node "$TRUTHSRC_CLI" generate-project --project truthsrc.project.json --out generated --plan --format human
node "$TRUTHSRC_CLI" generate-project --project truthsrc.project.json --out generated --format human
node "$TRUTHSRC_CLI" query-project --project truthsrc.project.json --out generated --knowledge SetCount --format human
node "$TRUTHSRC_CLI" verify-project --project truthsrc.project.json --out generated --format human
03

带着你的问题继续读

理解

为什么概念之外还要建模关系？

从 DDD 一致性边界出发，用真实银行子图做一次关系练习。

 阅读

一份声明长什么样？

跟随命令走过守卫、事件绑定与状态折叠，再了解语言的其他层次。

 构建

生成在哪里停下？

把知识、技术绑定、生成代码、手写集成与测试放进同一条生命周期。

 评估

付款成功就是投资成功吗？

沿声明看付款、TA 拒绝、独立退款与有界定投的不同职责。

 调查

能直接检查那些关系吗？

浏览真实节点与边，从场景进入声明，或查询随站点提供的 SQLite 快照。

 采用

如何与已有工具配合？

按工作任务比较，区分当前接口与尚在提案中的标准投影。
