全景

同类、互补，与隔壁的本体论

这个领域里有好邻居。诚实的定位是：有些工具我们互补，有些我们扩展，有一个我们对「模型」意味着什么持不同意见——但保持尊重。这里比的不是星数，而是每个工具各自身怀什么绝技。

同类们，按职责逐个看

项目它是什么许可 / 模式我们重叠之处我们不同 / 互补之处
EventCatalog事件驱动系统的 docs-as-code 把领域、服务、事件与 schema 渲染成可浏览的目录。v4 加了 agent/MCP 层。 MIT · open core 把事件驱动的知识当一等公民的图谱；MCP 供智能体访问——同一种直觉。 这个领域里最干净的一句话对比：EventCatalog 从你的架构生成文档；我们从知识生成架构本身——并锚定回去。他们的 Code-to-Docs agent 是 代码 → 文档；我们的闭环是 知识 → 代码 → 溯源。天然互补，不是对手。
ContextMapperDDD DSL（CML） 面向限界上下文、上下文映射、聚合的文本 DSL；生成 PlantUML / MDSL。 Apache-2.0 · 学术出身 基于文件的 DDD 建模加生成器——精神上最近的祖先。 CML 捕捉战略 + 战术的形状；它停在图和契约。我们的树编译成可查询的知识图谱、生成可编译的 CQRS 代码库、并用锚点证明血缘。CML 的产出可以作为真源树下游的投影之一。
proophPHP CQRS/ES 组件 · Event Engine PHP 的事件溯源工具箱；Event Engine 率先做到「写个模型，生成 ES 代码」。 MIT · 社区/混合 「模型 → 生成的 ES 代码」的抱负——他们证明了需求是真的。 他们的受众是 PHP 运行时的管道层；我们做的是任何运行时之上的知识层——带验证闸门、图谱查询、智能体访问和带锚点的往返。不同层，同一个信念。
QlerifyAI 辅助的协作建模 SaaS EventStorming 风格画布，AI 提议命令/事件/模型，导出 backlog + OpenAPI。 闭源 SaaS AI 辅助发现命令/事件/读模型——漏斗前端重叠。 对一份真实 Qlerify 导出的字段级分析：骨架齐全，行为空缺——聚合/事件/角色/查询能干净导出（15 种类型中 5 种完整），但不变量、守卫、错误码、saga 和流水线没有表示（其 strategy/decision/GWT 卡片是叙述文本，不是形式化的）。Qlerify 发现共识；真源树把它变成工业级产物。集成——包括反向导出回画布——已为它留好设计，在DEF-02 台账上。
EventStorming / Domain Storytelling发现方法论 工作坊形式：橙色事件、蓝色命令、角色、策略——或角色/工作物/活动叙事。 是方法，不是工具 我们的 inbox 笔记类型就是那套便签词汇——EventStorming 是正统的入口。 方法不是事实来源：墙的照片会腐烂。inbox 是工作坊产出的落点——机器可检验的草稿，等待人工晋升——这个发现层我们刻意不竞争，我们消化它。
Palantir Ontology企业语义层 企业数据之上的对象/链接/动作类型；动作写回；SDK 从类型生成；MCP 暴露。 闭源 从语义模型生成 SDK；「决策，不只是数据」；智能体访问——直觉高度一致。 封闭世界 vs 开放文件：他们的本体是你租用的产品；我们的树是你拥有的 YAML，编译成你带得走的代码。分类学优先 vs 关系优先——本站名字所指的那个哲学分岔。我们借鉴他们的治理思路（用量追踪、分阶段变更）；我们发布整个栈。

Qlerify 的覆盖率数字来自对一份真实导出 workflow.json 与我们 15 类型注册表的字段级比对——5 完整 / 6 部分 / 4 缺失。方法与矩阵见项目的研究笔记。

为什么要投影

投影是可再生的，所以可以为每个消费者采用最好的标准，而不需要树拥有 N 种方言。标准永远不会变成主人；树也永远不会分叉成 N 份各自漂移的文件。（MCP + SQLite 之外的投影生成器，排在台账上运行时闸门之后。）
