一、战略俯瞰（Level 0）：整座城池的宏观地形图

想在 metarch-truthsrc 里精准排雷，先要破除一个常见错觉：它不是一个“读 YAML 填模板”的脚手架工具，而是一座叠加了两个历史地层的五段式领域编译器。

  • 地层一（v1 严格治理遗产层，emitter/families/）：24 个经过 emitter/parity.mjs 金文件锁死的 Scala CQRS/Play 确定性代码发射器（值对象、聚合协议、Akka 持久化、Protobuf 编解码、Play 运行时等）。
  • 地层二（v2 EARS-Native 主干层，lib/ears/ + lib/v2/）：正交 YAML 结构加载器、EARS 1.0 词法/语法/绑定/Z3 SMT 求解器、DMN First-Hit 见证合成器、Canonical Model v2、本地 SQLite 知识图谱、TS/Scala 双栈与 Scala 单栈生成器、锁定 BDD 测试发射器、变异测试与防作弊门禁。

绝大多数真实 Bug 并不藏在某个函数内部的算法里，而是藏在“地层交界处”与“同一语义被多个下游独立翻译”的接缝上。下面这张战略地形图标出了从真源到运行时的六大主战区，以及红色虚线标注的四大高危断层带：

必须先建立的两个顶层心智模型

  1. 双栈（Dual-Stack）与 Scala 单栈（Single-Stack）的定位分工：
    • typescript 目标提供毫秒级 Node 22 零编译反馈、浏览器友好验证与教学演示；scala-cqrs-play-service-v2 是面向生产的 Akka/Play/Protobuf/ScalikeJDBC 完整服务交付栈。
    • 在 0b925ad 引入 lib/v2/target-resolution.mjs 后，Scala 生产项目不再被迫维护“双槽”（*.cloze.ts + *Impl.scala）——只要项目仅存在 generated-scaffold/scala（或 .truthsrc/generated-scala-manifest.json）而无 generated-scaffold/ts，tasks-v2、verify-v2 与 check-v2 会自动收敛为 Scala 单栈模式。
  2. 离线 scalac 与真实 sbt stage 的两层盲区差：
    • verify-v2 为了在秒级完成 TDD 闭环，走的是离线裸 scalac + ScalaTest，并主动剥离了依赖 Akka/Play/ScalaPB/ScalikeJDBC 的框架文件。
    • 这意味着离线 verify-v2 全绿 ≠ sbt -batch stage 能编过 ≠ Play HTTP 路演返回 200。Play 控制器、ReadSide 投影仓储、Protobuf Converter、Guice DI 模块与 conf/routes 只有在真实 sbt -batch stage + 启动 Play 进程时才会接受编译器与运行时的终极检验。

三、核心数据流与状态机（Level 2）：一条规则如何穿越全链路？

从宏观落到中观，要看清两条最关键的纵向数据通道和一个横向状态机——排雷时只要发现某条数据在不同节点被重新解析或重新推导，那里几乎必定存在分叉风险：

磁盘三域所有权边界（物理隔离铁律）

磁盘领地 所有者 生成器行为 guard-write.mjs 写守卫策略
truth/（YAML + .ears + bindings） 领域作者 / 架构师 只读输入，绝不回写 允许编辑（变更后须重跑 compile-v2）
generated-scaffold/、generated-tests/、projections/ 编译器与生成器 全量确定性覆写 物理阻断（TERRITORY_LOCKED，exit 2）
handwritten/（*Impl.scala、*.cloze.ts、ServerSnapshotProviderImpl.scala、HandwrittenBindingsModule.scala） 人类 / 隔离区 AI Agent 仅首次创建，已存在永不覆写（overwrite: false） 仅允许在 @cloze:start(<id>)..@cloze:end(<id>) 之间局部编辑，禁止整文件覆盖或修改标记
.truthsrc/（canonical-v2.json、knowledge.sqlite、manifests） 派生状态缓存 编译/验证阶段更新（重建 SQLite 时保留 provenance） 可清理重建，但 cloze_slots.provenance 记录验证与盲审凭证

四、地下暗道图（Level 3）：14 条最容易踩爆的跨文件隐蔽耦合

地面上的主干看起来井然有序，但真正让大项目（例如 6 子域、50 领域行为、23 个 @cloze 槽位的考试平台）在集成期撞墙的，是埋在地下的 14 条隐蔽暗道（T01–T14）。每一条暗道都对应一对“表面上互不调用、实则共享隐式不变量”的源码模块：

暗道网 A · 类型与名义系统断层（T01–T03）

  1. T01 · resolvedType.kind === 'record' 的六端重复翻译：
    • structure-loader.mjs 把 ExactType（如 Money、Score）与 ValueObject 统一编码为 { kind: 'record', typeName }。
    • 但下游至少 6 个文件各自写了一套 scalaTypeOf / defaultScalaExpr / buildNominalIndex：v1-strict-scala.mjs、v1-strict-block-cd.mjs、v1-strict-readside.mjs、v1-strict-policy.mjs、v1-strict-api-auth.mjs、witness-materialize.mjs。
    • 爆雷机理：只要任意一端漏掉 case 'record' 的 exactByName / voByName 查找，就会走 default: return 'String'——直接导致 Play ReadSide 把 String 赋给 BigDecimal/Long（Issue #2） 或 ReadModel 含 VO/ExactType 字段无法编译（Bug #4）。
  2. T02 · ReadSide 集合编解码的 SPEC-S10 双轨约束：
    • v1-strict-readside.mjs 在生成 ScalikeJDBC 读写代码时，对于原始类型序列（如 Vector[String]）必须保留 Json.stringify(Json.toJson(row.topics)) 与 Json.parse(...).as[Vector[String]]（受 SPEC-S10 锁定）；而当元素嵌套了 ExactType 或 ValueObject（无自动隐式 Play Format）时，必须通过 typeUsesNominal 分流到递归 jsEncodeExpr / jsDecodeExpr。
  3. T03 · aliases 必须恒含 'state' 的四处隐式假设：
    • 当 YAML 给聚合手写自定义 aliases: [bal] 而未显式列出 'state' 时，v1-strict-scala.mjs 和 witness-materialize.mjs 在展开 state.field 时会误把它当成嵌套记录成员，拼出 state.copy(state = state.state.copy(...))（Bug #7）。因此所有读取 agg.aliases 的位置都必须强归一化为 new Set(['state', ...])。

暗道网 B · 1.0 遗产家族与 2.0 桥接层断层（T04–T07）

  1. T04 · SBT_FRAMEWORK_IMPORT_RE 双份正则与离线 scalac 剥离暗道：
    • verify-gate.mjs:359 与 mutation-gate.mjs:210 各维护了一份框架 import 正则，把依赖 akka.*、play.*、scalapb.*、scalikejdbc.*、infrastructure.{proto,persistence.converters,...} 的文件从离线 scalac 中过滤掉。
    • 排雷铁律：每当新增或改造一个生成的 Scala 文件，如果它继承或引用了某个会被过滤掉的 trait（如零 VO 场景下的 DomainConverters.scala 继承 <Agg>ProtoConverters），它自身也必须携带匹配该正则的 import，否则 sbt stage 过了，离线 verify-v2 却会报 not found: type！同时改正则必须两处同步改。
  2. T05 · 1.0 emitter/families/ 24 家族金文件红线：
    • emitter/parity.mjs 锁死了全部 24 个 1.0 家族的正例字节输出与 runNegatives 负例契约（例如 proto-converter.mjs 明确断言 valueObjects.length === 0 必须抛错）。
    • 工程红线：遇到 v2 特有的退化形态（如全项目零 VO/ExactType），绝不能通过放宽 1.0 家族断言来迁就，而要在 v1-strict-block-cd.mjs 的 2.0 桥接层发射兜底实现，保住 1.0 24/24 allGreen。
  3. T06 · 混合 L1+L2 聚合的 RuleParams 统一与 SPEC-S4 零 Noop 铁律：
    • 同一个聚合若同时拥有 L1 纯规则与 L2 @cloze 计算规则，参数必须全部统一生成在 <Agg>RuleParams 下，不能分裂出 <Agg>DomainServiceRuleParams。
    • 同时，SPEC-S4 严禁非空 L2 <Agg>Computations trait 在生产代码提供 val Noop（防止线上误绑定空实现）。因此在 scala-strict-scalatest.mjs 中，L1 规则测试针对混合聚合必须传入 null.asInstanceOf[<Agg>Computations]（安全，因为 L1 分支永不调用宿主计算方法）。
  4. T07 · tools/lint.mjs 架构防污染门禁：
    • tools/lint.mjs 用正则静态扫描全部 626 个 JS/MJS 文件：严禁在通用核心出现业务专有名词（如 CreditBalance、FundOrder、bankwealth），严禁在 lib/runtime-profile.mjs 之外硬编码 net.imadz，严禁活跃 emitter/families/ 拼接硬编码 'app/' 路径。

暗道网 C · 见证物化与测试预言机断层（T08–T10）

  1. T08 · Z3 稀疏见证 → witness-materialize 具象填充语义失真：
    • first-hit-witness.mjs 只向 Z3 查询守卫表达式中实际出现的变量；其余字段全靠 witness-materialize.mjs 补全。
    • 两大陷阱：① 给接受规则构造有效集合需要非空样本，但若对拒绝规则（isRejected）也强制覆盖空数组 []，就会把 len(items) == 0 的拒绝见证彻底篡改失效（Bug #1）；② 应用层成功用例若缺少 bindPrincipal 注入、服务端 stateSnapshot 或给序列字段传了标量，就会引发批量失败（Issue #3）。
  2. T09 · 事件字段解析双口径：
    • 聚合事件可以显式声明 fields:，也可以由命令参数与数据血缘自动推导。若 v1-strict-scala.mjs 用 resolveCanonicalEventFields(agg, ev) 产出 case class，而测试发射器只读 ev.fields，[POSTCOND] 测试就会与真实事件构造器签名错位（Bug #6）。
  3. T10 · 5 层 Authz PEP/PDP 的四端镜像暗道： - onion-routes.mjs 派生路由后，onion-ts.mjs、onion-scala.mjs、v1-strict-api-auth.mjs（真实 Play 控制器）与 interfaces-http.mjs（HTTP 预言机）必须逐项对齐： - 首条路由是 public 时，401/403 测试必须挑第一条非 public 路由； - external-pdp 与 resource-policy 两种模式都必须向测试注入 allow-PDP； - GET 路由在 AUTHZ_* 用例中必须拼装 query string； - Play 控制器必须走 HttpStatusMapper.statusForRejection(err.code) 而非硬编码 400，递归转换 JsNull => null（PlayHttpBridge.scala），解析 X-Entitlements / X-Principal-Attr-*，并在服务端执行 ownerField（403）、requiresEntitlement（403）与 rowScope（403）及 ServerSnapshotProvider.load。

暗道网 D · 多域单体打包、目标解析与门禁断层（T11–T14）

  1. T11 · 单体打包 mergeCanonicalsForBc 的静默 dedupBy 吞并与旧文件残留： - 翻开 generators/scala-cqrs-play-service-v2/generate.mjs:135：合并多子域时，valueObjects、exactTypes、readModels、aggregates、ports、stories 全都用 dedupBy(..., x => x.name) 按短名去重。一旦两个子域定义了同名不同结构的 ValueObject 或 ReadModel，后者会被静默丢弃而非报冲突！此外，目录增量重生成不会删除旧包名/旧路由留下的孤立 .scala 文件（Issue #4）。

四步对抗探针排雷法

  1. 选暗道：从图 3 的 T01–T14 暗道中挑一个尚未被极端组合打过的跨模块接缝。
  2. 造最小对抗真源：只写 10–40 行最小 YAML + .ears，专门构造合法但反常规的边界组合（例如：零 VO、混合 L1+L2、嵌套 Option[ExactType]、Scala 保留字字段、两子域同名不同结构 VO）。
  3. 跑全链路真编译（严禁只跑正则单测）：在临时目录完整串跑：
    • compileCanonicalV2（Z3 真求解）
    • generateScalaCqrsPlayServiceV2 / generateScalaCqrsPlayServiceV2ForBc
    • emitV2ExecutableTests
    • node --test + 离线 scalac + 真实 sbt -batch stage + 启动 Play 进程发真实 HTTP 请求
  4. 实锤即上锁：确认 Bug 后先修通用推导（守 npm run lint:arch 0 违规 + emitter/parity.mjs 24/24 全绿），再把对抗样例固化为 SPEC-S26+，绝不靠人眼审查结案。
